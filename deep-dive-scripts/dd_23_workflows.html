1
What Workflows Are

Workflows are Rev.io PSA's automation engine. A workflow watches for a specific event to happen in the system — a ticket being created, a status changing, an SLA being breached, a time log being added — and then automatically sends a notification to a defined set of recipients. They are the mechanism for making sure the right people know about the right events without anyone having to manually remember to send a message.

A single workflow can now send multiple notification types simultaneously — email, SMS, and in-app notification — in one workflow rule. You no longer need separate workflows for each notification channel.

→ Connects ToWorkflows connect to: Tickets (most common trigger source), SLA Policies (SLA threshold and breach triggers), Time Logs (time entry created trigger), Calendar Events (event triggers), Users and User Groups (recipients), Contacts (external party notifications), Slack and Microsoft Teams (channel notifications), and SMS (requires SMS to be configured in System Settings).
2
Workflow Structure — Triggers, Conditions, and Reactions

Every workflow has three components: a Trigger, optional Conditions, and one or more Reactions.

Triggers — What Event Starts the Workflow

Trigger CategoryAvailable Triggers
TicketTicket Created, Ticket Updated, Ticket Closed, Ticket Activity Note Created, Ticket Sent to Billing
SLASLA Escalation Threshold Reached, SLA Target Breached
TimeTime Log Created, Time Log Updated
CalendarCalendar Event Created, Calendar Event Updated
BillingInvoice Created, Payment Received

Conditions — Narrow Which Events Fire the Workflow

Conditions filter the trigger. Without conditions, every event of that type fires the workflow. Conditions let you be specific: 'Only fire when Ticket Priority equals Critical' or 'Only fire when Ticket Type equals Break/Fix and Customer equals Acme Corp.'

Conditions use AND/OR logic. Multiple conditions can be stacked. This is what makes workflows precise rather than noisy.

Reactions — What Happens When the Workflow Fires

A reaction is a notification sent to a defined set of recipients. One workflow can have multiple reactions — for example, an email to the tech AND an SMS to the manager AND an in-app notification to the service team, all configured in the same workflow rule.

Reaction TypeDescriptionBest Used For
EmailSends a formatted email with subject and body using token-populated variablesFormal notifications, customer-facing updates, detailed internal alerts
SMSSends a short text messageUrgent alerts to field techs, dispatch notifications, on-call paging
In-App NotificationSends a notification inside Rev.io visible in the notification centerInternal team awareness, non-urgent updates
Slack / TeamsPosts a message to a configured Slack channel or Teams channelTeam-wide visibility, operations channels, service desk feeds
3
Recipients — Who Gets Notified

The recipient configuration determines who receives each reaction. Rev.io PSA offers several recipient options:

Recipient OptionWho It Includes
Assigned TechnicianThe primary tech assigned to the ticket
Associated TechniciansAll techs associated with the ticket, not just primary
Internal UsersSpecific named users selected from your user list
Internal GroupsAll users in a selected user group
Contact TypesContacts on the customer account by role — e.g., all contacts with the 'Billing Contact' type
External PartiesAll relevant contacts associated with the triggering event — e.g., primary contact + associated contacts on the ticket
Specific Email AddressA hardcoded email — useful for escalation addresses or shared inboxes
💡 Pro TipUse Contact Types and External Parties for customer-facing workflows rather than hardcoding specific contacts. This way the workflow always goes to the right person on the account, even if contacts change over time.
4
Workflow Tokens — Dynamic Content in Notifications

Workflow notifications are most useful when they contain specific information about the event that triggered them. Tokens are placeholders that populate with real data when the workflow fires.

Common Tokens

TokenPopulates With
[Ticket.ID]The ticket number
[Ticket.Subject]The ticket subject line
[Ticket.Status]Current ticket status
[Ticket.Priority]Ticket priority level
[Customer.Name]Customer account name
[Contact.Name]Name of the associated contact
[Tech.Name]Name of the assigned technician
[Ticket.WorkRequested]The Work Requested field content
[Ticket.URL]A direct hyperlink to the ticket in PSA

Tokens are inserted into the subject line and body of email reactions, and into the message text of SMS and in-app notifications. The token selector in the workflow editor shows all available tokens for the selected trigger type.

⚠ Watch OutThe [Ticket.URL] token generates a deep link directly to the ticket. This is extremely useful in internal notifications — your team can click straight through to the ticket without searching. Always include it in internal email and in-app notifications.
5
Building a Workflow — Step by Step

Navigate to Admin > Workflows > Add Workflow.

  • Give the workflow a descriptive name — 'New Ticket Created — Notify Assigned Tech' not 'Workflow 1'
  • Select the Trigger event
  • Add Conditions if needed to narrow when the workflow fires
  • Add a Reaction — select the notification type (Email, SMS, In-App, Slack/Teams)
  • Configure the recipients for this reaction
  • Write the subject and message, inserting tokens where relevant
  • Add additional reactions if you want multiple notification types from the same trigger
  • Save and activate the workflow
  • Test by triggering the event manually and confirming the notification arrives

7
Managing and Maintaining Workflows
  • Search and filter: The Workflows list has search and filter capabilities. Use descriptive names so workflows are findable as the list grows.
  • Activate/Deactivate: Workflows can be toggled on or off without deleting them. Useful for seasonal workflows or during testing.
  • Copy: Duplicate an existing workflow as a starting point for a similar one.
  • Test before activating: Always trigger the event manually after building a workflow to confirm the notification arrives correctly and contains the right information.
  • Audit regularly: Review workflows quarterly. Remove or update workflows that reference old statuses, users who have left, or processes that have changed.
⚠ Watch OutA workflow that fires on every ticket update with no conditions can generate significant notification volume. Your team will start ignoring everything if their inbox is flooded. Start with targeted, high-value workflows and add more as you learn what's useful.

Action Items

  • Identify your top 5 notification needs before the session
  • Build the starter workflows from the recommended list above
  • Configure Slack or Teams integration if your team uses those channels
  • Test every workflow after building it
  • Name all workflows descriptively so they're manageable as the list grows
  • Schedule a quarterly workflow review to prune stale or noisy notifications
